Please review the existing FloraWise repository carefully before making changes.

Do NOT rebuild the application from scratch and do NOT replace the existing architecture unnecessarily.

Update the current implementation while preserving existing working functionality, existing user data, authentication, calendar, recommendations, statistics, reports and administration.

The main goals of this update are:

1. simplify the process of adding a plant;
2. separate physical plant placement from geographic weather location;
3. support reusable user-defined places and saved geographic locations;
4. replace plant photo URLs with real image upload;
5. formalize the existing PlantSpecies directory as the FloraWise plant-care knowledge base;
6. make RecommendationEngine use structured species knowledge, care history, plant placement and weather consistently;
7. keep all functionality understandable and convenient for regular users.

All user-facing interface text, validation messages and recommendation explanations must remain in Ukrainian.

==================================================
1. SIMPLIFY PLANT CREATION
==================================================

The plant creation form should remain simple.

The regular user should provide only information specific to their particular plant.

The main form should contain:

- Назва рослини
- Вид рослини
- Фото рослини
- Місце розташування
- Погодна локація

Do NOT ask a regular user to manually enter:

- optimal temperature;
- humidity;
- watering frequency;
- light requirements;
- soil requirements;
- fertilizing frequency;
- pruning rules;
- transplanting recommendations;
- harvesting information;
- weather thresholds.

These values belong to PlantSpecies / the FloraWise knowledge base.

The user selects the species, and FloraWise automatically uses the stored knowledge for that species.

==================================================
2. USER-DEFINED PHYSICAL PLANT PLACES
==================================================

Replace the current free-text plant location approach with reusable user-defined places.

Create a PlantPlace entity:

PlantPlace
- id
- userId
- name
- environmentType

environmentType values:

- INDOOR
- BALCONY
- OUTDOOR
- GREENHOUSE

Examples:

- "Вітальня"
- "Підвіконня у спальні"
- "Балкон"
- "Сад біля будинку"
- "Теплиця"

Each Plant should reference a PlantPlace.

When adding or editing a plant, the user must be able to:

- select an existing PlantPlace;
- create a new PlantPlace directly from the plant form without leaving the page.

Suggested UI:

"Місце розташування"

[ Вітальня ▼ ]

"+ Додати нове місце"

When creating a new place, ask only for:

- Назва місця
- Умови розміщення

Suggested Ukrainian environment labels:

INDOOR -> "У приміщенні"
BALCONY -> "На балконі"
OUTDOOR -> "На відкритому ґрунті"
GREENHOUSE -> "У теплиці"

Do NOT ask the user to manually specify temperature, humidity, light level or environmental measurements for PlantPlace.

PlantPlace represents where the plant physically exists.

The user's saved locations must persist after logout/login.

Users must only see and manage their own SavedLocations.

8. CENTRALIZED WEATHER LOCATION RESOLUTION
==================================================

Keep weather location resolution centralized.

Create reusable logic similar to:

resolveWeatherLocation(user, plant)

For plant-specific weather and RecommendationEngine use:

plant explicitly selected SavedLocation
→ user's default SavedLocation
→ system fallback location

For dashboard weather use:

user's default SavedLocation
→ system fallback location

Do not hardcode Kyiv directly inside dashboard components or RecommendationEngine.

After the user changes the default location, dashboard weather should refresh for the selected location.

==================================================
9. USE PLANTPLACE ENVIRONMENT TYPE IN WEATHER RULES
==================================================

Weather-aware recommendations must also consider PlantPlace.environmentType.

For example:

Rain should be relevant to watering for an OUTDOOR plant.

Rain should NOT automatically postpone watering for an INDOOR plant.

Example:

IF:
- task.type == WATERING
- plant.place.environmentType == OUTDOOR
- precipitation exceeds the applicable threshold

THEN:
recommend postponing watering.

Use the same principle for other weather-sensitive tasks where relevant.

10. FORMALIZE PLANTSPECIES AS THE FLORAWISE KNOWLEDGE BASE
==================================================

FloraWise already has PlantSpecies / flora species data.

Do NOT create a completely separate duplicate knowledge system.

Extend the existing PlantSpecies model so it becomes the structured source of truth for plant-care knowledge used by:

- plant directory;
- plant details;
- recommended care planning;
- RecommendationEngine;
- administrator functionality.

Do NOT use an LLM or generative AI as the factual source of plant-care parameters at runtime.

RecommendationEngine must use structured knowledge stored in the FloraWise database.

AI-generated random care information must not replace stored plant knowledge.

==================================================
12. STRUCTURED SPECIES CARE RULES
==================================================

RecommendationEngine currently has global rule parameters.

Keep them as fallback values, but support species-specific care rules.

Create a model similar to:

SpeciesCareRule
- id
- speciesId
- careType
- rainThresholdMm nullable
- maxWindSpeedMps nullable
- minTemperature nullable
- maxTemperature nullable
- notes nullable

careType should match existing FloraWise care task types:

- WATERING
- FERTILIZING
- PRUNING
- TRANSPLANTING
- TREATMENT
- HARVEST
- OTHER

Rule priority:

species-specific SpeciesCareRule
→ global RULE_PARAMETERS fallback

This ensures that incomplete species data does not break recommendation generation.

Examples:

For outdoor tomato:

WATERING:
- reacts to significant precipitation.

TREATMENT:
- may have rain restriction;
- may have wind restriction.

HARVEST:
- may prefer a dry day.

For indoor Monstera:

Outdoor precipitation should not directly postpone watering.

PlantPlace.environmentType must still determine whether outdoor weather actually affects the plant.

==================================================

"Для цього виду поріг значних опадів становить 8 мм."

Other examples:

"Полив має високий пріоритет, оскільки останній полив було виконано 8 днів тому, тоді як рекомендований інтервал для цього виду становить 5 днів."

19. FIX LAST CARE HISTORY LOOKUP
==================================================

Correct the current logic for retrieving the latest completed care operation.

For watering recommendations:

Do NOT inspect care history only through the first currently planned watering task.

Instead:

1. find all WATERING tasks belonging to the selected plant;
2. use their completed CareLog records;
3. find the latest completedAt date;
4. provide this date to RecommendationEngine.

Create a reusable helper/service similar to:

getLatestCompletedCareAction(plantId, taskType)

The same mechanism should later support:

- last watering;
- last fertilizing;
- last pruning;
- last transplanting;
- other care types.

RecommendationEngine should use actual completed care history rather than planned task dates when determining how long it has been since the last care action.

30. DO NOT OVERLOAD THE USER
==================================================

The design principle should be:

The user describes their specific plant and where it is located.

FloraWise already knows the general characteristics of the species through the knowledge base.

Therefore:

USER ENTERS:
- personal plant name;
- species;
- photo;
- physical place;
- geographic weather location.

FLORAWISE KNOWLEDGE BASE PROVIDES:
- optimal temperature;
- humidity;
- watering recommendations;
- light requirements;
- soil requirements;
- fertilizing information;
- pruning information;
- transplanting information;
- harvesting information;
- species-specific recommendation rules.

CARE HISTORY PROVIDES:
- last completed watering;
- last fertilizing;
- last pruning;
- etc.

WEATHER SERVICE PROVIDES:
- temperature;
- precipitation;
- humidity;
- wind.

RECOMMENDATIONENGINE COMBINES ALL OF THE ABOVE.

32. FINAL IMPLEMENTATION PRINCIPLES
==================================================

Do not:

- rebuild unrelated parts of FloraWise;
- add unnecessary complexity;
- require latitude/longitude from users;
- require photo URLs;
- ask users to manually enter species knowledge;
- use random recommendations;
- use an LLM as the factual source for care parameters;
- silently create large care schedules;
- silently change care dates without confirmation;
- fabricate knowledge source URLs;
- break existing stored data.

Do:

- reuse existing application architecture;
- keep the plant form simple;
- keep physical and geographic locations separate;
- make locations reusable;
- keep species knowledge structured;
- make RecommendationEngine deterministic and explainable;
- use species-specific rules when available;
- fall back safely when detailed knowledge is missing;
- preserve existing FloraWise functionality;
- keep all user-facing content in Ukrainian.

Before considering the update complete:

- run database migrations;
- run seed/update logic safely;
- run type checking;
- run the application;
- run the production build;
- fix runtime errors;
- test the complete flows described above.

First review the current implementation and existing schemas/routes/components before changing anything, then implement these requirements incrementally without rewriting unrelated working functionality.
