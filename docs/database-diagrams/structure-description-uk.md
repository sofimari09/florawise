# Структура бази даних інформаційної системи FloraWise

## 1. Метод перевірки

Опис і діаграми підготовлено на підставі Drizzle-схем у `lib/db/src/schema/`, базового SQL-файлу `lib/db/drizzle/0000_flora_baseline.sql`, адитивних міграцій API та фактичних метаданих PostgreSQL у схемі `public` середовища розробки. Перевірено таблиці, колонки, первинні й зовнішні ключі, обмеження та індекси. Запити до бази були лише для читання; структура, міграції та записи не змінювалися.

## 2. Кількість і призначення сутностей

У схемі `public` на момент перевірки наявні **17 таблиць FloraWise**. Вони містять **15 обмежень первинного ключа** та **23 фізичні зовнішні ключі**. Дві junction-таблиці мають унікальні складені індекси, але не мають окремого первинного ключа.

| Таблиця | Призначення |
|---|---|
| `flora_users` | Профіль користувача FloraWise та його зовнішній ідентифікатор Clerk. |
| `flora_plant_places` | Іменовані місця розміщення рослин користувача з типом середовища. |
| `flora_saved_locations` | Збережені координати й короткі назви локацій користувача для погодних запитів. |
| `flora_species` | Довідник видів рослин, категорій, умов утримання та рекомендацій з догляду. |
| `flora_species_care_rules` | Структуровані правила догляду за видом і типом роботи, включно з погодними порогами та інтервалами. |
| `flora_knowledge_sources` | Бібліографічні та довідкові джерела; таблиця може мати необов’язковий прямий зв’язок із видом. |
| `flora_species_knowledge_sources` | Зв’язок багато-до-багатьох між видами та джерелами знань. |
| `flora_species_care_rule_sources` | Зв’язок багато-до-багатьох між правилами догляду та джерелами. |
| `flora_plants` | Рослини користувачів, їхня ідентичність, місце, середовище та посилання на погодну локацію. |
| `flora_tasks` | Планові завдання з догляду, датою, статусом, пріоритетом і лічильником перенесень. |
| `flora_care_logs` | Записи про виконання завдань і коментарі до них. |
| `flora_reminders` | Нагадування, прив’язані до завдань і дат. |
| `flora_recommendations` | Рекомендації для рослин, зокрема запропоновані погодні перенесення та їх застосування. |
| `flora_notifications` | Сповіщення користувача з необов’язковими посиланнями на рослину, завдання, нагадування чи рекомендацію. |
| `flora_reports` | Збережені звіти за період із агрегатами та необов’язковим JSONB-знімком деталей. |
| `flora_plant_photos` | Метадані завантажених фотографій та ідентифікатор власника Clerk; байти зображень у цій таблиці не зберігаються. |
| `flora_schema_migrations` | Версії застосованих міграцій схеми. |

## 3. Первинні ключі та фізичні зв’язки

Таблиці з `serial`-ідентифікаторами використовують `id` як первинний ключ. Винятки: `flora_plant_photos.object_path` є текстовим первинним ключем, а `flora_schema_migrations.version` — текстовим первинним ключем. Таблиці `flora_species_knowledge_sources` і `flora_species_care_rule_sources` не мають PK; унікальні індекси на парах FK не допускають повторення тієї самої пари.

Основні фізичні зв’язки:

- `flora_users` 1:N `flora_plant_places`, `flora_saved_locations`, `flora_plants`, `flora_reports` і `flora_notifications`. Для рослин FK `user_id` не задає `ON DELETE CASCADE`; для інших перелічених дочірніх таблиць FK користувача має каскадне видалення.
- `flora_species` 1:N `flora_species_care_rules`; також вид може мати багато рослин через необов’язковий `flora_plants.species_id`.
- `flora_species` 1:N `flora_knowledge_sources` через необов’язковий `flora_knowledge_sources.species_id`.
- `flora_species` M:N `flora_knowledge_sources` через `flora_species_knowledge_sources`.
- `flora_species_care_rules` M:N `flora_knowledge_sources` через `flora_species_care_rule_sources`.
- `flora_plant_places` і `flora_saved_locations` можуть бути пов’язані з багатьма `flora_plants`; відповідні FK у рослині необов’язкові та мають `ON DELETE SET NULL`.
- `flora_plants` 1:N `flora_tasks` і `flora_recommendations`.
- `flora_tasks` 1:N `flora_care_logs` і `flora_reminders`. `flora_recommendations.related_task_id` — необов’язковий FK на завдання з `ON DELETE SET NULL`.
- `flora_notifications` має обов’язковий FK на користувача та необов’язкові FK на рослину, завдання, нагадування й рекомендацію; видалення пов’язаних записів не видаляє сповіщення, а очищує відповідний FK через `ON DELETE SET NULL`.
- `flora_reports` належать користувачеві; унікальний індекс `(user_id, period_start, period_end)` забезпечує не більше одного запису звіту для тієї самої комбінації користувача й меж періоду.

Фізичних зв’язків 1:1 у поточній схемі немає. FK із необов’язковими значеннями показують, що дочірній запис може не мати відповідного батьківського запису.

## 4. Важливі відношення предметної області

Ланцюг догляду реалізовано як `flora_plants` → `flora_tasks` → `flora_care_logs` та `flora_reminders`. Рослина пов’язана з видом довідника через необов’язковий FK; для власних рослин `species_id` може бути відсутнім, а `category` обмежується окремим CHECK-обмеженням. Для видових рекомендацій таблиця `flora_species_care_rules` зберігає структуровані правила, а junction-таблиця `flora_species_care_rule_sources` зв’язує їх із джерелами.

Рекомендації зберігаються в `flora_recommendations`: обов’язково пов’язані з рослиною, але можуть мати необов’язкове посилання на завдання, початкову та запропоновану дати, час застосування і текстове поле `weather_json`. Окремої таблиці метеоспостережень або прогнозів немає. Координати та назви локацій зберігаються в `flora_saved_locations`; додаткові legacy-поля погодної локації наявні в `flora_users` і `flora_plants`.

Статистика не зберігається в окремій таблиці: агрегати обчислюються з даних завдань. `flora_reports` зберігає агреговані значення, а `report_details` типу JSONB може містити знімок деталізації; він не створює реляційних FK на рядки завдань. Типи статусів, пріоритетів, догляду й середовища переважно зберігаються як `text`, а не як PostgreSQL ENUM. Фізично на рівні CHECK зафіксовані перевірки допустимої категорії виду та узгодженості ідентичності рослини.

## 5. Зв’язки, що залежать від логіки застосунку

Нижче наведені правила не є фізичними FK або унікальними обмеженнями PostgreSQL:

- `flora_users.clerk_user_id` зберігає зовнішній ідентифікатор Clerk і має унікальне обмеження, але в базі немає таблиці Clerk і FK на її сторонню систему.
- `flora_plant_photos.clerk_user_id`, `flora_plants.photo_object_path` та шляхи завантаження не мають FK між собою чи на `flora_users`; перевірка власника фотографії та відповідності шляху рослині виконується застосунком.
- `flora_plants.user_id`, `place_id` і `weather_location_id` мають окремі фізичні FK, але схема не гарантує, що пов’язане місце або погодна локація належать тому самому користувачеві, що й рослина. Відповідність власника контролюється прикладною логікою.
- `flora_saved_locations.is_default` не має часткового унікального індексу, який обмежував би користувача однією стандартною локацією; вибір стандартної локації координує застосунок.
- `flora_reports.report_details` є JSONB-снимком, а не таблицею деталей із FK на завдання чи рекомендації.
- `flora_schema_migrations` і `flora_plant_photos` не мають формальних FK. `flora_plant_photos` пов’язується із зовнішнім сховищем і власником на рівні застосунку.
